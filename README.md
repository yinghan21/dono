# dono

**C++26 模块化工程的一体化工具。** 构建系统 · 构建插件 · 包管理 · 工具链管理 · 环境与运行时——五个角色，一个命令。

```console
$ dono new h
   Creating binary (application) `h` package
   Created C:\work\h

$ cd h && dono build
   Precompiling std module (gcc@16.2.0)
   Compiling src/main.cpp
   Linking target/debug/h.exe
   Artifact target/debug/h.exe
    Finished `debug` [unoptimized + debuginfo] in 13.34s

$ dono run -- hello world
Hello from h!
Built with import std + std::println on modular C++26.
  arg[1] = hello
  arg[2] = world
```

`import std;` 直接可用，不用写 CMake，不用手动预编译 BMI，不用管 `-fmodules`、`gcm.cache`、`-lstdc++exp` 这些细节。

## 0. 安装

**图形化安装向导**：`dist\dono-setup.exe`（1.25 MB = 向导 160 KB + 内嵌 dono.exe，无其他依赖，绿色单文件）。

![安装向导](docs/setup-options.png)

- 安装位置可编辑，旁边「浏览…」调系统文件夹选择框；勾选「为所有用户安装」时默认目录跟着变（`%LOCALAPPDATA%\Programs\dono` ↔ `%ProgramFiles%\dono`）；
- 「加入 PATH」默认勾选；没有管理员权限还勾「所有用户」会提示先提权；
- 点「安装」后原地显示进度条与阶段，完成后弹一次结果框，按钮变成「完成」。

![安装中](docs/setup-progress.png)

也可以命令行驱动（等价于点窗口）：

```console
$ dono-setup.exe                      打开向导（默认 %LOCALAPPDATA%\Programs\dono）
$ dono-setup.exe /D=D:\tools\dono     指定安装目录
$ dono-setup.exe /S                   静默安装（不弹窗，可在脚本里用）
$ dono-setup.exe /ALLUSERS            机器级安装（管理员，默认 %ProgramFiles%\dono）
$ dono-setup.exe /NOPATH              只放文件，不动 PATH
$ dono-setup.exe /UNINSTALL [/S]      卸载（不带 /S 会先弹确认框）
```

> 安装器是 GUI 子系统程序：在 **cmd** 里调用会等它退出；在 **PowerShell** 里要用
> `Start-Process dono-setup.exe -ArgumentList "/S" -Wait`，`&` 不会等图形程序结束。

它做四件事：

1. 把 `dono.exe` 复制到安装目录（同时放一份 `dono-setup.exe` 供卸载用）；
2. 把安装目录追加进 **PATH**：用户级写 `HKCU\Environment`，机器级写 `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`；保留原值类型（`REG_EXPAND_SZ`）并广播 `WM_SETTINGCHANGE`；
3. 在「设置 → 应用」登记卸载项（`DisplayName / DisplayVersion / InstallLocation / UninstallString / EstimatedSize / NoModify`）；
4. 幂等：重复安装视为升级，PATH 不会重复追加；卸载逐字还原 PATH、删注册表、删目录（自己正躺在目录里时交给一个分离进程收尾，避免"文件被占用"）。

```console
$ dono-setup.exe /D=D:\tools\dono
   ┌ dono 安装程序
   │  安装位置：D:\tools\dono
   │  作用范围：仅当前用户
   │  加入 PATH：是
   └

   · 安装到 D:\tools\dono
   · 已写入 dono.exe（1.1 MB）
   · 已加入 PATH
   · 已登记卸载项（设置 → 应用 里能看到 dono）

   安装完成：dono 0.1.0
   已打开的终端需要重开（或 refreshenv）才会看到 dono 命令。
```

重新打包：`powershell -File installer\build.ps1`（默认读 `target\release\dono.exe`，产物写到 `dist\`）。
安装器不内嵌 payload 时，会读同目录的 `dono.exe`，所以也可以当作"便携版安装器"用。

## 1. 定位

C++ 通常把下面五项工作交给五个工具，dono 用一个命令完成全部五项。

| | 构建系统 | 构建插件 | 包管理 | 工具链管理 | 环境与运行时 |
|---|---|---|---|---|---|
| **dono** | 内置（并行执行器 + Ninja 后端） | 模块 / std 模块 / 交叉目标规则 | `[github.Getlibrary]` + `dono.lock` | 探测 + registry + `--target` | std 模块缓存、runner、裸机模板 |
| 最接近的工具 | CMake + Ninja | CMake modules、xmake rules | vcpkg、Conan | rustup、nvm | conda、Nix |

设计取向和 cargo 一致：**约定优于配置**。不写 `[targets.h]`，dono 从 `src/main.cpp` 推断出 binary target，`dono test` 自动发现 `tests/*.cpp`。

## 2. 项目结构

```
h/
├── dono.toml             ← 工程描述
├── src/
│   └── main.cpp          ← import std; 直接可用
├── tests/
│   └── test_smoke.cpp    ← `dono test` 自动发现
└── target/               ← 构建产物（可整目录删除）
    ├── .last-result.json ← 最近一次构建的机器可读结果
    └── debug/
        ├── h.exe
        ├── build.ninja            ← 每次构建都生成，可直接 `ninja -C target/debug`
        ├── compile_commands.json  ← clangd / IDE
        ├── gcm.cache/std.gcm      ← 自动预编译并缓存的 std 模块
        ├── obj/src/main.cpp.o
        └── tests/test_smoke.exe
```

`dono new h` 生成的 `src/main.cpp`：

```cpp
// h — generated by `dono new`
import std;

int main(int argc, char* argv[]) {
    std::println("Hello from h!");
    std::println("Built with import std + std::println on modular C++26.");
    if (argc > 1) {
        for (int i = 1; i < argc; ++i) std::println("  arg[{}] = {}", i, argv[i]);
    }
    return 0;
}
```

`dono new ac` 生成同样的骨架，只是注释与问候语换成 `ac`。

`dono init` 等价于 zig 的 `zig init`：在**当前目录**直接生成工程，工程名取目录名（可用 `--name` 覆盖）。
它只补缺失的文件——目录里已有 `src/main.cpp`、`tests/`、`dono.toml` 时会原样保留（`--force` 才覆盖），所以拿它接管一个已有工程是安全的。

加依赖可以写全 `dono add imgui <url>`，也可以直接 `dono imgui <url>`（第二个参数是 git URL 时自动当作 `add`）。

## 3. 命令

| 命令                                    | 作用                                                                    |
| ------------------------------------- | --------------------------------------------------------------------- |
| `dono new <name>`                     | 新建工程；`--template` / `-t` / `--bin` / `--lib`（互斥）、`--demo`、`--vcs git` |
| `dono init`                           | 在当前目录生成工程（只补缺失文件，已存在的原样保留）                                            |
| `dono build`                          | 编译 debug                                                              |
| `dono build --release`                | 编译 release（默认 `-O2 -DNDEBUG`，可用 `--opt` 覆盖）                           |
| `dono run [-- args...]`               | 编译并运行                                                                 |
| `dono test [filter]`                  | 编译并运行 `tests/` 下的每个测试                                                 |
| `dono clean [--all]`                  | 清理 `target/`（`--all` 连 `.dono` 状态一起清）                                 |
| `dono add <key> <url>`                | 添加 `[github.Getlibrary]` 依赖并立即拉取（简写：`dono <key> <git-url>`）           |
| `dono remove <key>`                   | 移除依赖                                                                  |
| `dono fetch` / `dono update`          | 拉取 / 更新依赖并写 `dono.lock`                                               |
| `dono tree`                           | 打印依赖树                                                                 |
| `dono toolchain list`                 | 本机可用工具链 + 目标支持表                                                       |
| `dono toolchain install <family@ver>` | 安装工具链；也接受目标三元组：`dono toolchain install --target riscv64-none-elf`     |
| `dono toolchain default <family@ver>` | 设置全局默认                                                                |
| `dono toolchain which`                | 本次构建会选哪个编译器、为什么                                                       |
| `dono doctor`                         | 环境 / 工具链 / std 模块 / BMI 缓存诊断                                          |
| `dono why <topic>`                    | `runners` \| `toolchain` \| `std` \| `target`                         |
| `dono metadata`                       | 打印工程元数据（JSON）                                                         |

`--template` 的边界情况都明确报错（退出码 2，且**不落盘任何文件**）：

```console
$ dono init --template
error: --template 需要一个值
$ dono init --template --lib
error: --template 需要一个值（后面跟的是 --lib）
$ dono init --template=
error: --template 需要一个值（等号后面是空的）
$ dono init --template bin --lib
error: --template / -t / --bin / --lib 只能指定一个
$ dono init --template nope
error: 未知模板 'nope'（可选：bin | lib | multi-module | riscv-virt-rt）
```

build / run / test 共用选项：

```
--release            优化构建
--target <triple>    交叉目标，例如 aarch64-linux-musl
--toolchain <spec>   gcc@16 / llvm@20 / msvc
-j <N>               并行任务数（默认 CPU 并发）
--opt <0|1|2|3|s>    优化级别（debug 默认 0，release 默认 2）
--timings            打印最慢的任务，用于定位编译时间
--backend <b>        auto | ninja | direct
--configure-only     只刷新 build.ninja 与 compile_commands.json
--force              忽略增量缓存
--keep-going         单个文件失败后继续
--offline            不联网（依赖必须已 vendor）
--update             先更新依赖
-v / --verbose       打印调度决策、depfile、探测细节
```

## 4. dono.toml

```toml
[package]
name = "h"
version = "0.1.0"
edition = "2026"        # 2020 | 2023 | 2026 | latest | fly
description = "h — created by dono new"
authors = []

[build]
compile_commands = true # 在工程根目录放一份 compile_commands.json 副本
# backend = "auto"      # auto（有 ninja 就用）| ninja | direct
# target  = "x86_64-linux-musl"
# toolchain = "llvm@20"
# cflags   = []
# cxxflags = []
# ldflags  = []
# libs     = []
# include  = []
# defines  = []
# std_mode = "auto"     # auto | module（强制 import std）| compat（强制头文件兼容层）
# target_dir = "target"

[toolchain]
# 按平台指定，优先于自动探测
# linux  = "gcc@16"
# macos  = "llvm@20"
# windows = "gcc@16"

[github.Getlibrary]
# 目录名 = 仓库地址；拉取后位于 Getlibrary/<目录名>
imgui = "https://github.com/ocornut/imgui.git"

# 想固定版本就用表形式
[github.Getlibrary.gui]
git = "https://github.com/ocornut/imgui.git"
rev = "v1.90.9"

[dependencies]
# 预留：版本化依赖，目前只解析、不参与求解（见 §10）
```

### [github.Getlibrary] 的语义

- **键名就是目录名，每个依赖一个独立目录**：`imgui = "..."` → `Getlibrary/imgui/`，`AndroidSurfaceImgui = "..."` → `Getlibrary/AndroidSurfaceImgui/`。互不覆盖、各自带自己的 `.git`，`Getlibrary/` 下永远只有一层：

  ```
  Getlibrary/
  ├── imgui/                 ← 独立仓库，remote = ocornut/imgui
  └── AndroidSurfaceImgui/   ← 独立仓库，remote = Bzi-Han/AndroidSurfaceImgui
  ```

- 浅克隆（`--depth 1`）到 `Getlibrary/<key>`，实际 commit 写进 `dono.lock`；下次构建沿用锁定版本，`dono update` 才动它。
- 检出目录自动加入 include 路径：`<dir>`、`<dir>/include`、`<dir>/src`（存在几个加几个）。所以 `#include "imgui.h"` 不用写任何路径。
- 如果供应商目录里有 `dono.toml`，dono 把它当成**包**：它的 `src/*.cpp` 会一起编译并链接进来（排除带 `main` 的翻译单元）。
- `Getlibrary/` 已经在生成的 `.gitignore` 里——依赖不进你的仓库。

`dono add` 会插到 `[github.Getlibrary]` 段内的条目区，不会把你的示例注释和 `[dependencies]` 挤散：

```toml
[github.Getlibrary]
imgui = "https://github.com/ocornut/imgui.git"
AndroidSurfaceImgui = "https://github.com/Bzi-Han/AndroidSurfaceImgui.git"
# 固定版本用表形式：
# [github.Getlibrary.gui]
# ...
```

`dono.lock`（自动生成，勿手改）：

```toml
[github.Getlibrary.gui]
url = "https://github.com/ocornut/imgui.git"
rev = "8c8b8fc266e8cd7fac09340c0373abc28732adb0"
```

## 5. 构建引擎

### 两个后端，同一份计划

dono 先把工程算成一张**任务图**（Job：argv + cwd + 输入 + 输出 + 依赖），然后：

- `direct`（**默认**）：dono 自带的多线程调度器，拓扑顺序 + 依赖计数唤醒，不依赖任何外部工具，输出风格统一；
- `ninja`：把同一张图写成 `target/<profile>/build.ninja`，交给 Ninja 并行执行（dono 能自动发现 PATH 之外的 ninja，包括 Visual Studio 自带的那份）；
- `auto` = `direct`；要用 ninja 就 `--backend ninja` 或 `[build] backend = "ninja"`。

无论用哪个后端，**`build.ninja` 每次构建都会重新生成**，你也可以随时自己 `ninja -C target/debug`。

默认走内置执行器的原因很实际：输出是我们自己的样式，不会混进 `ninja: Entering directory` 和 `[4/4]` 这种前缀：

```console
$ dono run
   ┌ dono · a v0.1.0
   │  debug · unoptimized + debuginfo · gcc@16.2.0 · x86-windows-gnu
   └  2 tasks · target/debug
   Compiling src/main.cpp
   Linking target/debug/a.exe
    Finished `debug` in 2.77s · 2 tasks · target/debug/a.exe
   Running target/debug/a.exe
Hello from a!
```

无改动时只剩一行：`    Finished \`debug\` in 0.09s · up to date`。

两个后端的增量语义一致，行为等价。**`build.ninja` 每次构建都会重新生成**，你也可以直接 `ninja -C target/debug`。

### 三层增量

1. **前端脏检查**：每个任务的指纹 = `argv + 源文件 mtime/size + 依赖任务指纹`。指纹不变且产物存在 → 跳过。`--force` 强制全量。
2. **逐文件 depfile**：编译命令始终带 `-MMD -MF`；dono 自己解析 depfile（相对路径按任务的 cwd 解析），任何头文件比产物新 → 重编。头文件被删也判脏。
3. **BMI copy-if-different（restat）**：std 模块 BMI 与缓存比对内容，内容相同就不改动时间戳，避免无谓地把下游全部标脏。

实测：冷构建之后，第二次 `dono build` 输出 `Finished ... (up to date)`，不产生任何编译或链接动作；改一个头文件只重编引用它的那个翻译单元。

### import std 全自动

这是 dono 存在的首要理由。以 GCC 为例，`import std` 需要先有 BMI：

```
g++ -std=c++26 -fmodules -fsearch-include-path bits/std.cc -c   # 产出 gcm.cache/std.gcm
```

dono 自动完成这一步，并且：

- **带指纹的全局缓存**：`~/.dono/cache/bmi/<fingerprint>/gcm.cache/std.gcm`，指纹 = 编译器路径 + 版本 + 标准标志 + profile + 目标三元组 + `bits/std.cc` 时间戳。跨项目共享，第二个工程直接命中（`hardlink`，同盘零拷贝），13.4s 的 std 预编译变成 0s。
- 编译所有任务时 `cwd = target/<profile>/`，GCC 的 `gcm.cache/` 就在那里，模块解析稳定可控。
- 自动补 `-lstdc++exp`（`std::println` 的 `__open_terminal` / `__write_to_terminal` 在这个库里）。

### 模块

- 认识 `.cppd` / `.cppm` / `.ixx` / `.mpp` 为模块接口单元。**这些扩展名编译器并不认识**，dono 会显式加 `-x c++`（MSVC 用 `/TP`），否则 GCC 只会给一句 `linker input file unused` 的警告然后什么也不产出。
- 扫描 `export module X;`、`module X;`、`export module X : part;`、`import X;`、`export import :part;`、`import std;`，据此做拓扑排序，保证接口单元与分区先编译。
- 每个翻译单元的依赖描述可以导出成 **P1689r5** 形状（`emit_p1689`），供外部工具/未来的 dyndep 使用。
- 接口单元编出的产物若没真的生成对象文件，执行器会判失败并打印编译器输出——不会假装成功。

### 速度：时间花在哪里

单个 hello-world 翻译单元（GCC 16.2 / MinGW，`import std`），本机实测：

| 阶段 | debug | release |
|---|---|---|
| dono 规划（manifest / 工具链 / 扫描 / 生成计划 / ninja 调用） | 0.06 s | 0.06 s |
| gcc 编译（含解析 32 MB `std.gcm`） | 2.6 s | 6.9 s |
| 链接 | 0.2 s | 0.2 s |

也就是说 **时间几乎全部在 GCC 解析 std 模块 BMI 和 `-O2` 优化上**。dono 自己的开销从最初 1.4 s 降到 0.06–0.08 s，做法：

- 进程内解析 `PATH`/`PATHEXT`，不再为每次查找 spawn `where.exe`；
- 工具链探测结果以「编译器路径 + 文件时间戳」为键落盘缓存（版本、模块支持、`import std` 能力、std 源码位置），命中时零进程；
- `host_triple` 同样落盘缓存；
- MSVC 改用目录探测，不再每次 spawn `vswhere.exe`；
- `--configure-only` 从 1365 ms 降到 84 ms，空跑 `dono build` 从 1490 ms 降到约 140 ms。

可调项：

- `--opt 1`：release 构建 6.9 s → 4.6 s（实测）；
- `-j N`：多翻译单元时线性加速；
- 只改一个文件时，增量只重编那一个 TU（见 §5 三层增量）；
- `--timings` 打印最慢的任务（direct 后端给出逐任务耗时，ninja 后端给出 plan/build 拆分）。

### 进度显示

- **默认（内置执行器 + 交互终端）**：单行进度条原地刷新。完成部分是绿色 `█`，正在跑的任务用一段青色"巡航光块"扫过，避免长时间停在 0% 看起来像卡死：

  ```
     [████████████████────────]  67%  2/3  12.4s  |  Compiling src/engine.cpp
  ```

  配套 ANSI 颜色：`Finished` 绿、时间青、辅助信息灰。字符集刻意只用 GBK 里存在的 `█ ─ ┌ │ └ ·`，中文控制台不会出现问号。
- **重定向 / CI**：颜色与 `\r` 控制符全部自动关闭，退化成逐行 `Compiling xxx`。
- **ninja 后端**（`--backend ninja`）：直接继承 stdio，ninja 自己的 `[3/7] Compiling ...` 实时可见。

强制开关：`DONO_FORCE_COLOR=1` 开彩色、`NO_COLOR=1` 关彩色、`DONO_FORCE_TTY=1` 假装是终端（用来在管道里预览进度条）。

### 其他

- **没有 `main` 就是库工程**：`src/` 里找不到 `main` 时，`dono build` 不链接可执行文件，而是打包 `target/<profile>/lib<name>.a`（MSVC 为 `<name>.lib`）并说明原因——而不是把链接器那句 `undefined reference to WinMain@16` 丢给你。空源文件也会提前警告。
- **控制台编码**：Windows 上按控制台活动代码页（`GetConsoleOutputCP`）转码输出，重定向到文件/管道时输出 UTF-8。`stdout` 与 `stderr` 走同一条通道，所以 `error: …` 也不会乱码；`> build.log` 里仍是 UTF-8。
- **C 是一等公民**：自动识别 `.c`，用 `-std=c17`、`$CC` 编译，和 C++ 对象一起链接，支持 C/C++ 混合工程。
- `compile_commands.json`：写在 `target/<profile>/`，路径记录在 `target/.last-result.json`；`[build] compile_commands = true` 时在工程根目录再放一份副本。`--configure-only` 可在不编译源码的情况下刷新它。
- `target/.last-result.json`：`ok / profile / target / toolchain / std_module / compiled / skipped / failed / artifacts / compile_commands / timestamp`。

## 6. 工具链

身份是 `family@version`，`family ∈ gcc | llvm | msvc`。dono 只修正**自己选择的**默认值：你在 `dono.toml` 里显式写下的 `[toolchain]` 永远按原样生效。

### 按宿主选择默认值

| 宿主 | 候选顺序 |
|---|---|
| Windows（检测到 Visual Studio） | `llvm → msvc → gcc`（MinGW-w64） |
| Windows（无 VS） | `gcc → llvm → msvc` |
| Linux x86_64 | `gcc → llvm` |
| Linux aarch64 | `llvm → gcc` |
| macOS | `llvm → gcc` |

候选不是"看到就算"，而是**探测后择优**：能预编译 std 模块（`import std`）的候选优先。`dono why toolchain` 会把完整决策链打出来：

```
why this toolchain?
  · tried llvm@19.0.1 -> usable (no import std)
  · family msvc -> 1 candidate(s), none usable — cl.exe 已找到，但 INCLUDE/LIB 未设置
  · tried gcc@16.2.0 -> usable (import std ok)
  · target x86-windows-gnu (host)
  · selected gcc@16.2.0 [C:\mingw32\bin\g++.exe]
```

### 隔离沙盒

所有下载的工具链位于 `~/.dono/registry/toolchains/<family>/<version>/`，不改动系统 PATH、不动系统编译器。

```console
$ dono toolchain install gcc@16 --dry-run
[dry-run] resolved payload: https://github.com/dono-lang/toolchains/releases/download/gcc-16/gcc-16-x86-windows-gnu.zip
[dry-run] target dir: C:\Users\...\.dono\registry\toolchains\gcc\16

$ dono toolchain install gcc@16 --from D:\payloads\gcc-16      # 离线：从解包目录装
$ dono toolchain default gcc@16
```

也可以直接按**目标三元组**装——dono 会从支持表里查出该目标的约定工具链（表里写 `android-ndk@30`、`emsdk@6.0.9` 这类非编译器家族也认）：

```console
$ dono toolchain install --target aarch64-linux-android
note: 目标 aarch64-linux-android 的约定工具链是 android-ndk@30（verified）
已经可用：android-ndk@r28c（系统安装于 C:\Users\Admin\android-ndk\android-ndk-r28c）
note: 注意：系统里的是 r28c，与你请求的 30 不完全一致；dono 会直接使用系统这一份

$ dono toolchain install x86-windows-gnu
x86-windows-gnu 就是宿主三元组，本机 gcc@16.2.0 已经能产出它，无需安装

$ dono toolchain install --target riscv64-none-elf --dry-run
note: 目标 riscv64-none-elf 的约定工具链是 llvm@23（verified）
note: 本机该家族已装：llvm@19.0.1（不是 llvm@23）
[dry-run] resolved payload: …/llvm-23/llvm-23-x86-windows-gnu.zip

$ dono toolchain install android-ndk@30 --from D:\ndk\android-ndk-r30
   已安装 android-ndk@30 -> C:\Users\…\.dono\registry\toolchains\android-ndk\30

$ dono toolchain install riscv64-linux-musl
error: 目标 riscv64-linux-musl 尚未接通（tier: planned）
```

——注意它不会拿 `llvm@19` 冒充 `llvm@23`：版本不匹配就是"未安装"，并告诉你本机该家族有哪些版本。给了 `--from` 就表示你明确要装这一份，不再做"已经可用"的短路。

### `toolchain list` 的来源记号

一眼看出哪份是系统自带的、哪份是 dono 装的：

```console
$ dono toolchain list
installed toolchains (host x86-windows-gnu):
     id                    usable  import std  source  compiler
  *  gcc@16.2.0            yes     yes         PATH    C:/mingw32/bin/g++.exe
     llvm@19.0.1           yes     no          NDK     C:/Users/…/android-ndk-r28c/…/clang++.exe
     msvc@19.51.36260      no      no          VS      C:/Program Files/…/cl.exe
                                                    └ cl.exe 已找到，但 INCLUDE/LIB 未设置…
     * = 当前会选中（gcc@16.2.0）
     source: PATH = 系统 PATH 里的；VS = Visual Studio 自带；NDK = Android NDK；dono = ~/.dono 里装的

registry: C:/Users/…/.dono/registry/toolchains
  （空）—— 上面能用的工具链都来自系统；`dono toolchain install <spec> --from <dir>` 装到这里
```

`*` 是"当前目录下构建会选中的那一个"；`source=dono` 的行同时会在 registry 段落里带 `← dono 装的` 标注。

### std 兼容层

工具链没有模块化标准库时（例如 Clang 未提供 libc++ 的 `std` 模块），dono 不会让你卡死：它把 `import std;` 改写为包含 `<dono/std_compat.hpp>` 的副本再编译（原文件不动），并在构建时明确告知：

```
note: std 兼容层已启用：2 个源文件的 `import std;` 被改写为头文件包含（工具链 llvm@19.0.1 不支持 import std）
```

兼容层头文件用 `__has_include` 逐个守卫（`<print>`、`<format>`、`<ranges>`、`<expected>`…），能编到哪就包到哪。`[build] std_mode = "module"` 可以强制要求真模块（不满足就直接报错），`"compat"` 可以强制走兼容层。

### 交叉编译

`dono build --target <triple>` 一个选项，dono 负责选编译器与标志：

- **LLVM**：本身就是交叉编译器，dono 追加 `--target=<triple>`；
- **GCC**：必须是交叉工具链，dono 去找 `<triple 前缀>-g++`（也认 `i686-w64-mingw32-g++` 之类的经典前缀）；找不到就明确失败并给出两条出路，而不是悄悄编出宿主二进制；
- **MSVC**：不支持从本平台交叉到任意目标，直接说明。

裸机目标不带操作系统：C 库、启动代码、内存布局、模拟器由板级支持包提供（`--template riscv-virt-rt` 就是一个例子），dono 只负责编译、链接与 runner 调度。

## 8. 模板

```console
$ dono new h                          # bin：src/main.cpp + tests/test_smoke.cpp
$ dono new mylib --template lib       # 纯库：src/mylib.cppd（模块接口单元）+ tests/test_smoke.cpp
$ dono new mylib --template lib --demo  # 同上，另加演示用的 src/main.cpp
$ dono new mm --template multi-module # 模块 + 模块分区（export module mm : ops;）
$ dono new blinky --template riscv-virt-rt   # 裸机：board/virt.cpp、board/virt.ld、[runners]
$ dono init --lib                     # --bin / --lib 是 --template 的别名
```

| 模板 | 产出 | `dono build` 的产物 |
|---|---|---|
| `bin`（默认） | `src/main.cpp`、`tests/test_smoke.cpp` | 可执行文件 |
| `lib` | `src/<name>.cppd`、`tests/test_smoke.cpp` | `target/<profile>/lib<name>.a`（**纯库，没有 main**，与 `cargo new --lib` 一致） |
| `lib --demo` | 上述 + 演示用 `src/main.cpp`（注释里标明可删） | 可执行文件 + 静态库 |
| `multi-module` | 模块接口 + 分区 + `main.cpp` | 可执行文件 |
| `riscv-virt-rt` | `src/main.cpp`、`board/virt.cpp`、`board/virt.ld`、`[runners]` | 裸机 ELF |

`lib` 模板的测试会真的 `import <name>;`，所以它同时验证了模块能被编译并链接：

```cpp
// tests/test_smoke.cpp — 由 `dono new --template lib` 生成
import std;
import mylib;

int main() {
    check(mylib::add(2, 3) == 5, "mylib::add(2, 3) == 5");
}
```

CLI 打印的文案跟随模板：`Creating library (module) \`mylib\` package` / `Creating binary (application) \`h\` package`。

`multi-module` 生成的拓扑会被 dono 正确排序（分区先编、接口次之、`main.cpp` 最后）：

```
   Compiling src/mm/ops.cppd
   Compiling src/mm.cppd
   Compiling src/main.cpp
   Linking target/debug/mm.exe
```

## 10. Runner 与运行时

无法在构建机上直接跑的目标（裸机、wasm、移动端）用 runner：

```toml
[runners]
run = "qemu-system-riscv64 -machine virt -bios none -kernel {bin} -nographic"
```

```console
$ dono run --target riscv64-none-elf        # 自动使用 [runners] run
$ dono run --runner flash                    # 显式指定
$ dono run --list-runners
$ dono why runners                           # 解释发现顺序
```

判定顺序：`--runner <name>` → 交叉目标且有 `[runners] run` → 直接执行。`{bin}` 会被替换成产物绝对路径。

## 12. 已知边界

- **MSVC**：能通过 vswhere 定位 `cl.exe` 并如实报告，但需要 `INCLUDE/LIB`（即 Developer Command Prompt 或 `vcvars64.bat`）。没进 vcvars 时 `dono toolchain list` 会显示 `msvc@… no`，并说明原因，不会假装可用。
- **Clang 的 `import std`**：libc++ 的 `std` 模块需要预构建 `std.pcm`。dono 支持用 `DONO_STD_CPPM=<path/to/std.cppm>` 指定，否则自动走 std 兼容层。
- **`[dependencies]`**：只解析、不求解。版本化依赖解析器（registry + semver + 多版本共存）是下一步。
- **`toolchain install`**：从 GitHub Release 模板 + `--from` 离线目录安装。本机 `curl` 的 TLS 在代理环境下可能失败，此时用 `--from`。
- **Ninja 的 `deps = gcc` 故意不用**：GCC 的模块化 depfile 里会出现 `std.c++-module` 这类**逻辑名**，ninja 会把它当缺失文件从而永远判脏。dono 改为自己解析 depfile、把真实存在的头文件写进 `build.ninja` 的边（CMake 式做法）。
- **裸机/`none-elf`**：dono 负责编译、链接、runner 调度；C 库、启动代码、内存布局由板级支持包提供。
- 宿主是 i686 时，`--target x86_64-windows-gnu` 需要真正的 64 位交叉 gcc；dono 不会把 32 位产物当作 64 位。

## 13. 源码结构

dono 自己就是一个 dono 工程（`dono.toml` 在仓库根），可以用自己构建自己：

```console
$ dono build                  # → target/debug/dono.exe
$ dono build --release
$ dono test
```

```
src/
├── main.cpp        CLI 分发、help、new/init/build/run/test/clean/add/remove/fetch/tree
│                   toolchain/doctor/why/metadata
├── cli.cpp/.hpp    参数解析与模板选择（独立出来，dono test 直接测边界情况）
├── util.cpp/.hpp   平台探测、进程执行、文件、路径、日志、进度行、FNV-1a 指纹
├── toml.cpp/.hpp   TOML 子集解析（表、点号键、数组、内联表、字符串转义）
├── manifest.cpp/.hpp  dono.toml 模型、[github.Getlibrary]、dono.lock、文本级插入/删除
├── toolchain.cpp/.hpp family@version、三元组表、探测与缓存、编译/链接标志、
│                   std BMI 构建命令、交叉目标处理、registry 安装
├── graph.cpp/.hpp  源发现、模块扫描（接口/分区/import）、拓扑排序、P1689 输出
├── engine.cpp/.hpp 任务图、内置并行执行器、Ninja 生成、三层增量、
│                   compile_commands.json、.last-result.json
├── deps.cpp/.hpp   Getlibrary 拉取/锁定、包识别
└── scaffold.cpp/.hpp new/init 四种模板
installer/
├── dono-setup-gui.cpp  Win32 图形安装向导（单文件：向导 + 尾部追加的 dono.exe payload）
└── build.ps1           编译 + 附加 payload + 校验，产物写到 dist\

tests/
├── test_smoke.cpp  TOML 解析、模块扫描、入口检测、指纹、三元组归一化的冒烟测试
└── cli_audit.ps1   端到端 CLI 审计（69 个场景：成功路径 + 错误路径），`powershell -File tests\cli_audit.ps1`
```

依赖底座的选择：**没有引入 xlings/mmcp 这类外部运行时**——dono 的"工具链 / 包管理底座"是 `~/.dono/` 下的 registry + cache 两棵目录树，加上 PATH/vswhere/registry 三路探测。好处是单文件二进制、零依赖、可完全离线；代价是工具链 payload 的构建与分发要自己维护（`--from` 是给这一步留的口子）。
